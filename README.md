# Bobo

Bobo 是一套面向可信局域网小团队的轻量项目管理系统。它以甘特图为主要工作区，组织“系统 -> 项目 -> 需求 -> 阶段”，并在阶段下维护负责人、进度和轻量 Jira 式问题。应用可在 Windows 或 macOS 上双击启动，浏览器访问，不依赖数据库、前端框架或第三方运行时包。

## 项目特征

使用范围仅为桌面浏览器，无手机使用需求。后续默认不为手机端、移动端或窄屏适配额外开发、优化或安排专项验收；已有适配保留现状，除非用户另行明确要求。

- 甘特图主视图：日期横轴，系统、项目、需求、阶段纵向分层；支持折叠、拖动排序、日期标记、悬浮摘要和双击编辑。
- 轻量问题协作：问题支持待处理、处理中、已关闭，包含负责人、优先级、截止日期、评论及操作人/时间审计。
- 局域网头像登录：普通成员点击头像免密进入，管理员使用至少 4 位密码；登录列表按系统折叠，成员可关联一个或多个系统。
- 清晰权限边界：成员只能访问关联的系统；管理员管理账户与系统，并执行项目、需求、阶段和问题的结构性删除。
- 本地多文件数据：系统索引、账户、项目和问题分别保存为 JSON，采用原子写入、全局 revision 与实体 version，便于备份和排查。
- 零依赖运行：服务端只使用 Node.js 内置模块，前端为原生 HTML、CSS 和 JavaScript，适合 Windows 与可信内网。
- 克制的红色品牌主题：红色用于品牌、选择和主要交互；甘特阶段、状态和日期标记的业务颜色保持独立，不随主题色改变。

## 快速运行

要求 Windows 或 macOS，以及 Node.js 18 或更高版本；无需执行 `npm install`。

Windows 双击仓库根目录的 `run.bat`；macOS 双击 `run.command`，启动后自动打开浏览器。请保留启动终端窗口，服务在其中前台运行。也可以在终端运行：

```powershell
npm start
```

只启动服务、不自动打开浏览器：

```powershell
npm run start:no-open
```

macOS 启动脚本优先使用 PATH 中满足要求的 Node.js；否则查找 Homebrew、官方安装位置、Volta 和 nvm（支持 `NVM_DIR`，从已安装版本中选最高主版本），不会自动安装软件或修改系统配置。当前终端的 Node.js 过旧时，也可直接运行 `./run.command`。自定义启动示例：

```bash
./run.command --no-open
HOST=127.0.0.1 PORT=4180 BOBO_DATA_DIR=/absolute/path/to/bobo-data ./run.command
NODE_BINARY=/absolute/path/to/node ./run.command
```

`HOST` 默认 `0.0.0.0`，`PORT` 默认 `4177`，`BOBO_DATA_DIR` 默认仓库的 `data/`；脚本从仓库根目录启动，相对数据路径也以此为准。如下载或复制后可执行权限丢失，在仓库目录执行 `chmod +x run.command`。若 macOS 拦截下载文件，请在系统安全提示中确认来源并允许打开。

默认地址为 [http://localhost:4177/](http://localhost:4177/)。首次启动且没有有效管理员时，系统会进入独立初始化页；创建管理员后会自动进入工作台。服务默认监听局域网网卡，终端会打印其他设备可访问的 IP 地址。首次使用时需在 Windows 防火墙中允许 Node.js 的专用网络访问。

停止服务可以使用本机管理员工作台右上角的“关闭”，或在启动服务的终端按 `Ctrl+C`。如果端口被占用，启动会报错退出；请先关闭原服务进程或设置其他 `PORT` 后重试。不要让多个进程同时使用同一数据目录。

## 账户与登录

- 登录页按系统折叠普通成员，关联多个系统的成员会出现在对应的多个分组中；管理员集中显示在“管理员”分组。
- 普通成员由管理员创建，无密码，点击单字头像直接进入；管理员点击头像后输入密码。
- 管理员访问全部系统。普通成员至少关联一个系统，只能查看和操作其关联范围。
- 每个账户有一个可修改的单字头像。账户删除为逻辑删除，历史问题、评论、负责人和关闭记录仍保留原身份。
- 最后一名有效管理员不能删除、停用或降级，管理员也不能删除自己。
- 会话使用 HttpOnly、SameSite Cookie，服务重启或 24 小时后需要重新登录。

免密头像登录仅适合可信局域网。不要把当前配置直接暴露到互联网。

## 数据结构

```text
data/
├─ meta.json                       # schema 版本、全局 revision、更新时间
├─ systems.json                    # 系统、系统日期标记、项目顺序和版本
├─ users.json                      # 账户、头像、系统关联和密码哈希，Git 忽略
├─ users.example.json              # 无凭据示例
├─ attachments/                   # 附件二进制及逐文件元信息（运行数据）
├─ logs/attachment-deletions.jsonl # 附件过期删除审计日志
└─ projects/
   └─ <project-id>/
      ├─ project.json              # 项目、需求、阶段、标记和实体版本
      └─ issues.json               # 问题、评论和问题版本
```

个人选中项、折叠状态、日期范围和面板宽度保存在按账户隔离的浏览器 `localStorage`，不会写入共享业务数据。所有 JSON 写入先落临时文件再原子替换。旧版 `data/projects.json` 首次启动时会先备份到 `data/backups/` 再迁移。

备份时应在服务停止后复制整个 `data/` 目录。恢复时同样先停止服务，再整体替换，避免项目与 revision 不一致。

## 更新程序的操作顺序

1. 停止旧服务，确认所有使用同一数据目录的 Bobo 进程都已退出。
2. 覆盖新版程序文件，保留原 `data/`、`data-full-backups/` 及自定义数据目录，不能用发行包中的示例数据覆盖业务数据。
3. 运行**新版** `upgrade-data.bat`（Windows）或 `upgrade-data.command`（macOS），先核对实际数据目录及待改/待删清单，再输入 `UPGRADE`。脚本先全量压缩备份并校验，再补字段和清理所列停用旧文件；提示无需升级时直接进入下一步。任何报错应先处理，不继续启动。
4. 使用 `run.bat`（Windows）或 `run.command`（macOS）启动新版服务，刷新浏览器。
5. 管理员可访问 `/api/admin/diagnostics`，核对进程启动时间、程序/数据目录和源码指纹；离线磁盘检查使用 `node scripts/diagnose-data.js`。

升级和启动必须使用一致的 `BOBO_DATA_DIR`、`PORT`；双击脚本默认操作程序目录的 `data/` 和端口 4177。本次字段版本保持 v2，报表人工补充不写业务 JSON，无需为它单独运行迁移。复制程序文件不会自动替换正在运行的 Node 进程。

## 业务 JSON 字段升级（Windows / macOS）

历史数据可在**停止所有使用该数据目录的 Bobo 服务后**，Windows 双击 `upgrade-data.bat`，macOS 双击 `upgrade-data.command`。入口先列出待升级文件，输入 `UPGRADE` 才执行，其他输入取消。要求 Node.js 18+；macOS 与启动入口一样支持自动查找及 `NODE_BINARY`，两个入口都支持 `BOBO_DATA_DIR`、`PORT` 和命令行参数。

命令行默认只检查，不写入业务文件：

```bash
node scripts/upgrade-data.js --check
node scripts/upgrade-data.js --check --data-dir /absolute/path/to/bobo-data
# 确认服务已停止后实际执行；PORT 应与该服务一致
node scripts/upgrade-data.js --apply --data-dir /absolute/path/to/bobo-data --port 4177
```

当前字段补全版本为 **v2**，保留原多文件布局 `schemaVersion: 2`，补齐系统、项目、需求、阶段、日期标记、问题和评论的缺失字段，包含需求 `completed`、阶段 `recurrence` / `notificationText` 等；在 meta 中记录 `dataFieldsVersion`。已有值、ID、顺序、备注、历史姓名、状态和未知扩展字段保留，不以当前时间伪造业务历史。发生字段补全的实体提升 version，整体 revision 提升一次；重复运行无变化，不重复备份或提升版本。账户凭据、附件、日志、历史备份不参与补全。

升级先在系统临时目录规划、验证结构。实际执行时，**先对整个业务数据目录制作 `.tar.gz` 全量压缩包并逐项校验内容与 SHA-256**，通过后才补齐 JSON 或删除停用旧文件。默认全量包位于仓库的 `data-full-backups/`；自定义数据目录时位于该目录同级的 `<数据目录名>-full-backups/`，避免备份递归包含自身。包内包括账户凭据、附件、日志、未知文件和此前的 `data/backups/`，仅排除运行时 `.bobo-data.lock/`；符号链接按链接保存、不跟随外部目标。备份目录及文件限制访问权限，备份包应妥善保管。

随后将待改、待删原文件另按原字节备份到 `data/backups/fields-v2-时间-随机ID/`，记录修改/删除清单、原文件 SHA-256 和全量包位置；全量包同名 `.manifest.json` 包含完整文件清单。写入使用现有数据层的 UTF-8 原子替换；压缩备份或验证失败时不开始改写/删除。普通写入或删除失败时尝试回滚，并报告备份路径，回滚失败时明确提示人工恢复。突然断电或强制终止可能留下部分写入：停服后先保留故障现场，再将全量包解压到空目录，核对后整体恢复业务数据；也可按逐文件 manifest 恢复受影响文件。

旧版单文件 `projects.json` 先在临时副本使用现有迁移逻辑转换。全量包验证和 JSON 写入成功后，自动删除根目录中已停用的 `projects.json` / `projects.json.migrated`；只使用明确清单，不猜测任意 JSON 或未登记项目目录是否废弃，账户、附件元信息、日志及历史备份不清理。旧文件保存在全量包及逐文件备份中。缺失实体 ID、无效日期、损坏的当前业务 JSON、归属冲突或比当前程序更新的格式会停止升级，留待人工核对。脚本不会初始化空业务目录。

实际升级检查配置端口并获取数据目录锁；新服务同样持锁，避免服务和升级器并行写同一目录。旧版服务可能没有目录锁，因此必须停服且设置一致的 `PORT`；端口被其他程序占用时也会拒绝升级。正常退出释放锁，异常终止后通过原进程 PID 检查恢复过期锁。此脚本不会启动服务，也不会触发附件过期清理。

后续每次变更业务 JSON 结构，必须同步增加 `lib/data-upgrade.js` 的 `DATA_FIELDS_VERSION`、补全规则、`FIELD_HISTORY`、回归测试及文档，入口脚本继续复用同一升级器。

## 阶段与问题

在“编辑需求”弹窗点击“已完成”，确认后名称显示删除线，并移动到所属项目需求列表底部；再次编辑可点击“恢复未完成”。完成标记仅作用于需求，不批量改变阶段和问题状态，也不自动改写报表中的阶段完成率或 Todo。

“编辑项目”弹窗中的“需求顺序”列出当前未删除需求，可用上移、下移调整，点击“保存项目”后持久化。未完成与已完成分别排序，已完成组始终在底部；关闭弹窗会放弃排序草稿。需求状态、项目名称和排序保留服务端权限及版本冲突检查；项目排序冲突后明确选择保留草稿重试时，会合并最新成员列表，保留其他人新增的需求，不恢复已删除项。

阶段左侧的 `≡` 仍用于同一需求内排序，拖动预览包含整条阶段行（名称与甘特条），原位置淡显并提示插入位置。点击名称旁的编辑按钮后，输入非空名称可保存；清空或只保留空格时，管理员的按钮切换为红色 `×`，点击并确认后删除阶段及关联问题/评论。空名称按 Enter 只聚焦删除按钮，需再明确确认；按 Esc 可放弃编辑。普通成员不能使用此删除入口。名称编辑期间的外部更新只提示，不覆盖输入。

在需求下新增阶段或双击甘特空白处时，阶段默认使用“自定义”模式；保存后阶段类型与标题一致。负责人既可从当前系统的有效账号中选择，也可直接输入外部人员姓名。阶段编辑弹窗使用右上角 `×` 或 `Esc` 关闭。

新建需求恢复自动添加“需求澄清、工作量及商务、功能开发、技术测试、业务测试”五个默认阶段（可由 config/stage-types.json 配置），从当天起按每段两天顺序排期；每个阶段可独立编辑，也可按需增加自定义阶段。待处理问题仍需手动创建。未来日期本身不会生成问题，删除的问题不会因项目、需求、阶段保存或整状态保存而自动补回。阶段标题前的红点表示存在未关闭问题，绿点表示当前没有未关闭问题。问题支持：

- 标题、描述、状态、优先级和可选截止日期。
- 单一负责人，候选人按当前系统权限过滤。
- 创建、更新、关闭和重新打开的操作者与本地时间展示。
- 追加式评论；提交后不编辑、不删除，以保留审计历史。
- 状态、优先级、负责人和逾期筛选；筛选只影响当前阶段列表。

## 周期日期标记与重复任务

日期标记区点击“+”，选择系统/当前项目、名称、开始日期、颜色及重复方式。支持每周、每两周、每月，以及每隔 N 天/周/月；按周可选择多个星期，必须填写重复截止日。例如开始 `2026-11-01`、每周二、截止 `2026-12-31` 可一次设置两个月的项目会。列表中点击“✎”再次编辑，将截止日改为 `2026-11-30` 后，12 月标记随规则移除，不会留下散落的单次标记；也可改为“不重复”。

双击甘特任务条，在阶段详情的“周期性重复”中设置规则；开始/结束是首期模板，后续每期保留相同日历天数，在同一行显示多段任务条，重叠的周期会分行排列。双击任一段编辑整个系列，可修改周期、截止日期或取消重复。重复系列共享标题、负责人、工时、状态和问题，不提供逐期独立完成或单次例外。报表仍按一个阶段及首期计划日期统计，不展开周期待办。

截止日包含当天，按每次开始日期判断，因此最后一期结束可晚于截止日。双周以开始日期所在周的周一为周期锚点；每月按开始日号重复，不存在该日的月份跳过（如 31 日不会移到月底）。范围内必须至少有一次匹配，最多十年且不超过 1000 次。规则保存在原标记/阶段的 `recurrence` 字段，旧单次数据继续兼容，不需迁移；资源写入和兼容整状态写入均由服务端校验规则，保留 revision、version、权限和并发冲突处理。日期标记并发重试仅合并当前标记，保留同一列表中其他人的标记。

## 阶段附件与通知

双击任务条打开阶段弹窗，切换“附件”选项卡。通知文本框可直接粘贴内容，点击“保存通知”独立保存；切换选项卡不会清空草稿，关闭弹窗前请保存。通知文本最多 100000 字符，按纯文本保存，不执行 HTML；保留阶段 `version` 冲突提示，保存通知和上传附件不会清空详情页未保存输入。

可点击文件区域选择多个文件，或拖放多个任意格式文件，按顺序上传，单个文件最大 50 MiB。上传后立即落盘，列表中点击文件名下载；同名文件分别保存，不覆盖。附件默认位于 `data/attachments/`，设置 `BOBO_DATA_DIR` 时随业务数据目录移动；二进制以随机 ID 的 `.blob` 文件保存，原始文件名、大小、归属、上传人和服务器时间记录在同 ID 的 JSON 元信息中。列举、上传和下载均校验登录与系统访问权限，上传检查阶段版本，文件下载使用附件响应及 `nosniff`，不会在 Bobo 页面内执行 HTML 文件。

每次启动服务，在开始监听前自动清理**上传时间早于六个日历月前**的受管附件（按 UTC 时间计算，月末向目标月最后一天收敛，恰好位于边界的保留）。通知文本和其他业务数据不受清理影响。删除日志追加在 `data/logs/attachment-deletions.jsonl`，记录删除时间、动作、附件 ID、原文件名、项目/阶段、上传时间、清理边界和失败原因；先写 `delete_started`，再执行删除并记录 `deleted` 或 `delete_failed`。无法写入审计日志时不开始删除；启动清理失败会在服务终端报错。日志保留，不随附件一起清除。

阶段或项目被删除后，附件不再允许下载，磁盘文件保留至后续启动时按相同规则过期清理；不提供手动删除附件入口。附件和日志属于本地运行数据，已加入 Git 忽略；备份整个业务数据目录时一并包含。当前不提供文件内容扫描、在线预览或断点续传，单进程内存接收上传，适合现有可信局域网小团队使用。

## 轻量报表与工作交接

在工作台顶栏点击“报表”，可切换“状态概览 / 工作交接 / Todo 清单”。默认统计当前项目，也可切换为当前系统全部项目；不提供跨系统汇总。打开或点击“刷新数据”时通过现有授权接口读取一次最新快照，预览和导出共用其生成时间、统计日、范围与 revision，不包含未保存编辑，也不会自动跟随后台更新。

- **状态概览用于阶段性进展汇报**：展示所选系统/项目的阶段进展、原始状态分布、阶段备注、问题和风险；不按交接周期裁切，也不还原历史某日的状态。已完成阶段占比只是阶段数量比例，不是项目真实完成率；没有阶段时显示 `—`。
- Todo 将每条未关闭问题列为一项；未完成且没有开放问题的阶段才生成阶段提醒。今天到期不算逾期，问题的截止日不从阶段结束日推断；异常状态、无效日期和孤立问题显示待核对提示。
- **工作交接用于周期待办移交，Todo 用于周期执行安排**：默认本周，可快捷选择本周、下周或自定义日期（周一至周日，包含首尾，精确到本地日历日），也可选择全部日期。问题按自己的截止日落在区间内筛选，阶段提醒按计划开始/结束与区间相交筛选；阶段日期不完整时按有效结束日筛选并标注待核对。
- 无有效截止日期默认排除并显示排除数量；“包含无有效截止日期”“包含期前遗留未完成”均为可选项，默认关闭。额外纳入的事项有单独标签，且不会把尚未逾期的事项改成逾期。交接和 Todo 的待办、风险、摘要及各格式导出共用同一筛选；阶段是否生成提醒仍按全部开放问题去重，避免已有问题的阶段被重复代表。
- 报告仅在页眉左上角保留一次 Bobo 标识，标题使用“工作交接报告 / 状态概览报告 / Todo 清单报告”，页脚和快照说明不重复显示系统名称。
- **人工补充待办与风险**：可直接在相应分节的文本框添加、修改或清空多行内容，空快照也能填写，每节最多 10000 字符。工作交接支持待办和风险两项，Todo 支持补充待办，状态概览支持补充风险。人工文字单独标注，不改变快照事项数量、原始状态、统计、筛选或新增比较；不会转为系统问题/阶段。
- 人工补充随 Markdown、CSV、HTML 和打印/PDF 导出；CSV 追加“人工补充待办 / 人工补充风险”列，即使没有快照事项仍保留补充。切换模式、日期、范围或刷新数据会保留草稿，人工文字不按日期自动筛选，调整条件后请自行核对；关闭报表后清空。
- 交接以交接待办、相关风险和人工说明为主，默认不附完成清单；需要时可勾选“附带已完成 / 已关闭清单”。完成清单同样按计划日期筛选，不能当作某周实际完成的历史记录，也不会推算阶段完成日期。
- 待办排序支持风险/截止日优先、记录创建时间倒序、导入基准后的“本次新增在前”。创建时间仅来自问题的记录，阶段没有创建时间时靠后，历史迁移时间也不等于实际新建时间。
- **导入上次 HTML 比较新增**：只在本机读取新版 Todo/工作交接 HTML 的基准元数据，不运行文件脚本、不上传文件、不保存到业务库。按系统/项目 ID、事项类型与原始 ID 对比，标注“新增纳入 / 内容变更 / 上次已有”；新增纳入不等于新建，也可能是移期、重新打开或新生成的阶段提醒。上次清单本次未出现的数量只作提示，不据此推断已删除。
- 导入时要求范围一致，并自动恢复原文件的日期和附加选项；随后改变日期、范围或附加选项会清除比较。未导入基准时不标注新增；旧版 HTML 没有基准元数据，需先导出新版作为今后比较基准。基准、排序和区间在预览及全部导出格式中可见，文件名附日期区间与 revision。
- Markdown、CSV 和独立 HTML 可直接下载。Markdown 的 Todo/完成清单使用 `- [ ]` / `- [x]`；CSV 增加 `☐` / `☑` 的“完成勾选”列及“勾选来源”，保留中文 BOM、公式防护、原始 ID 与快照元信息，不含评论正文和账户凭据。交接/Todo 的 CSV 导出筛选后的待办与选中的完成清单；状态概览的 CSV 导出全部阶段与问题状态明细，阶段进展也始终包含已完成阶段。空清单仍保留一行快照元信息，事项字段为空。
- 预览中的 Todo 可以临时勾选，下载文件和打印版会带上当前勾选状态。已完成/已关闭事项按原始状态预勾选且不可取消；临时勾选不会改变原始状态、完成时间或快照统计，在刷新数据或关闭弹窗后清空。统计遵循当前模式的范围与日期口径；附完成清单开关只控制附加清单，不改变统计。
- “导出 HTML”生成包含全部样式和操作脚本的单文件，可在断网或服务关闭后打开，继续编辑人工补充、勾选/取消勾选，再用“保存报告副本”下载包含当前文字和标记的 HTML（文件名附“已编辑”）。离线编辑默认只在当前页面内存中，保存副本后才会写入下载文件；不使用浏览器存储，也不会连接系统服务。导入 HTML 比较时只读取原始快照基准，不导入人工文字，不覆盖当前补充草稿。
- “导出 PDF”调用浏览器打印窗口，请选择“另存为 PDF”。正文按 A4 排版，表头跨页重复，操作控件和编辑文本框不参与打印，人工补充以完整的多行正文显示；待办保留打印后可手写勾选的方框，已有勾选也会打印。此 PDF 是打印文档，不是带交互表单的 PDF，也不由 JS 直接下载生成。
- 预览、HTML 和 PDF 使用同一套报告样式：红色品牌页眉、摘要数字、分节标题、原始状态标签和斑马纹表格；窄屏按事项逐项展示，保留原始 ID 和归属信息。

例如 2026-10-30 周五选择“下周”（11 月 2 日至 8 日）导出 HTML，保留原文件；下周补充待办后刷新数据，导入这份 HTML，系统恢复同一周期并将新增纳入项排在前面，再另存新清单。手工勾选只属于文件办理标记，不代表系统任务已关闭，也不影响新增比较。

人工交接说明、分节人工补充和导入基准只在报表弹窗内存中保留，关闭即丢弃，不写回业务数据或浏览器存储。报告为当前快照，不能还原历史日报。报表不增加后端 API、业务 schema、持久化模型或第三方依赖；读取失败或日期无效后清空旧预览并禁用导出，恢复后重新启用。

## 多人协作

浏览器每 5 秒检查全局 `revision`。没有编辑弹窗时自动刷新；编辑期间只提示外部更新，不覆盖当前输入。系统、项目、需求、阶段和问题各自携带 `version`，同一实体并发修改时服务端返回 `409`，前端可加载服务器版本或基于最新版重试。

`PUT /api/state` 保留为手动保存兼容入口。资源写入与问题审计应优先使用资源级 API；普通成员提交过滤后的状态时，服务端会合并其无权访问的系统，避免误删其他系统。

## 无 Git 的版本与数据诊断

复制源码后，已运行的 Node 进程不会自动重载后端。内网排查先确认旧进程已停止，再从预期目录启动，并保持 `BOBO_DATA_DIR` 与 `PORT` 设置一致；只刷新浏览器不能确认后端已更新。账户和业务 JSON 留在原目录，**不要为排查删除或重置 data**。

管理员登录后，在同一服务地址打开 `/api/admin/diagnostics`（例如 `http://内网地址:4177/api/admin/diagnostics`）。返回只读诊断信息：进程 PID、启动时间、程序/实际数据目录、启动时与当前磁盘的代码指纹、变化文件、`restartNeeded`、schema/字段版本及按项目汇总数量，不包含密码、Cookie、通知或问题正文。普通成员不能访问。

未启动服务时，在本机和内网复制后的程序目录分别运行：

```bash
node scripts/diagnose-data.js
# 使用自定义业务数据目录时显式指定
node scripts/diagnose-data.js --data-dir /absolute/path/to/bobo-data
```

该命令只读，不初始化、迁移、升级或清理。对比两端 `source.id` 与逐文件 `source.files`；文件原字节相同才有相同指纹，不依赖 `.git`。命令输出标记 `read-only-disk`，只能证明磁盘文件，运行实例仍以管理员接口的 `sourceAtStartup` / `sourceOnDisk` 和数据目录为准。`dataFieldsVersion` 是数据字段补全版本，不是程序版本；`futureStagesWithoutIssues` 等计数用于核对旧自动逻辑的触发条件，不代表 JSON 已损坏。启动终端也会打印代码指纹、PID 和实际数据目录。

两处历史自动行为来源已确认：五阶段模板自 `022129a`（2026-07-07）存在于前端 `addRequirement`；问题补建函数自 `11fc716`（2026-07-14）存在，`a7d554d`（2026-07-15）将未来日期纳入补建条件并扩展到资源写入。按最新确认保留五阶段自动排期，已移除问题补建路径。配置 `config/stage-types.json` 提供默认阶段及类型选项；已生成的阶段存于各项目 `project.json`，问题存于同目录 `issues.json`，不会自动删除这些历史记录。

## 开发约定

- 保持 Node.js 内置模块与原生前端架构，未经明确架构决策不引入框架、数据库、构建工具或第三方运行时依赖。
- 业务写入统一经过数据层，保留 UTF-8 JSON 原子替换、迁移前备份、全局 `revision` 和实体 `version`；版本冲突返回 `409`，不得静默覆盖。资源级 API 优先于兼容的整状态保存。
- 权限由服务端校验，成员限定在关联系统内，结构性删除仅限管理员；账户逻辑删除并保留历史身份，问题评论仅追加，审计操作者与时间由服务端生成。
- 个人视图状态留在浏览器，按账户隔离；界面保持紧凑、响应式，品牌红色不得覆盖甘特和状态的业务颜色。编辑期间发现外部更新时保留用户输入。
- 自动化及浏览器验收使用独立 `BOBO_DATA_DIR` 和临时端口；不得修改真实数据，不提交账户凭据、备份、迁移产物、日志、缓存或本机业务数据变化。
- 按变更风险验证功能，运行自动化测试、关键脚本语法检查和 `git diff --check`；涉及界面的变更检查桌面浏览器布局与相关交互，不安排手机专项验收。

完成新功能或重大问题修复后，执行者需要按变更风险完成测试，更新 README 与交接文档，并按用户授权提交、推送当前开发分支。未授权时交付本地改动；测试或推送失败时必须明确记录失败原因和剩余工作。Agent 的具体执行约定见 [AGENTS.md](AGENTS.md)。
